# The window's bench

Every job the window's makers run, one script each, in the Linux VM only, `look.sh` aside, which only copies to the VM and asks it: a Mac never installs, builds, tests or opens the window. Each runs from any copy of the repository with no argument, and shares one cache, `$STATION_BENCH` (`~/bench` by default). Go's module and build caches are the one exception: each copy keeps its own under `.artifacts/go/`, seeded on its first run from the bench's `gomod/` and `gocache/` (hard-linked, else copied), so two copies building at once never write the same Go cache; its directories are writable (`-modcacherw`), so `rm -rf` removes a copy.

Several lots share the VM: each window takes a display of its own, and `npm run preview:proof` a free port, printed when it starts.

## What a recording holds

Two runs of `record.py` write the same requests, the same gestures and the same plain call answers.
They do not write the same watches: the world build has no fixed clock (`apps/engine/wire/world_on.go`), so a watch the engine ends before a check settles (`accounts.list`, `disk.read`) answers pending in one run and settled in the other, and a gesture's reads follow.
The recorder keeps a watch's first and last answers, skips the reads of `TIMED` after a gesture, and carries `engine.start`'s process number over from the last recording: nothing else is rewritten, since the rest is the engine's answer.
A watch the engine never ends (a VM being created streams its overview for as long as the birth lasts) is cancelled by its id after `QUIET` seconds of silence, as the window cancels a watch it lets go of, and its answers are those that came before.
So record only what your lot changed, `--call=<call>` for a gesture and `--only=<call> --in=<json>` for one read, and leave a churned file you did not mean to touch out of your commit.

## Starting a lot

The window is a member of the root's npm workspace, so a copy of the worktree is all the bench needs. From the Mac, copy it without its `.git`, then set up and prove in the VM:

```bash
rsync -a --delete --exclude .git --exclude node_modules --exclude target --exclude .artifacts ./ design:window-<lot>/repo/
ssh design 'cd window-<lot>/repo/apps/window && bash scripts/check.sh'
```

`check.sh` and `check-quick.sh` run `bench-setup.sh` first, so a copy synced again needs nothing else.

Run `check.sh` once WITHOUT `--update` before your first change: its failures are the ones you start from, and a golden that `--update` rewrites later is then yours to read, never one you inherited unseen. Once you change a page, `--update` rewrites its goldens, and you look at each before you commit it.

A test waits on a region (`within(region('…'), content('…'))`, a heading, a button by its name), never on a text that a row splits across elements: `content()` matches one element's text, so a sentence drawn as a title, a chip and a sentence is never seen whole, and the wait times out.

## The root's findings

The root's count is not the window's to clear: a finding outside `apps/window` belongs to the root's gate, `make check`. It is 0 on a fresh copy, as it is on the main it was cut from, every copy resolving `@jterrazz/typescript` 12.2.0 (measured 2026-11-13 in the VM `design`). The window's layers are not in that count: the root's check does not read them yet ([the dependency rule](../README.md#the-dependency-rule)).

## How long the Tauri window takes to open

About 30 s from the debug binary's exec to its Station window mapped, under Xvfb and openbox in the VM `design`, each run with a fresh sandbox HOME and display over `serve-world.py two-macs`; its first connection to the engine follows 0.6 s later. Measured 2026-11-13, three runs each, the binary built with `--features tauri/custom-protocol`:

| Head                                      | Window mapped (s)   | First connection (s) |
| ----------------------------------------- | ------------------- | -------------------- |
| `8e42fdf00`, before the law and core lots | 30.20, 30.21, 30.21 | 30.85, 30.86, 30.86  |
| the merge of both lots                    | 28.55, 30.21, 30.23 | 29.14, 30.84, 30.87  |

The merge is not slower. The wait is the same to a hundredth on every run: HYPOTHESIS 2026-11-13, a timeout of the environment (a D-Bus or portal call) the webview waits out, not work of the window; one run under `strace -f -tt -e trace=connect,poll,ppoll` shows which call it waits on.

## What stays behind

- In `$STATION_BENCH`: `npm-cache/`, `pw/` (Chromium), `gomod/` and `gocache/` (only read, to seed a copy's own), `worlds/` (one world build per state of the Go sources), `noreserve/` (the shim). Kept on purpose: it is what makes the next copy set up in seconds; `rm -rf ~/bench` empties it.
- In `$STATION_BENCH`, also `tauri-target/`: the Tauri build and the bridge's test build every copy shares, a few gigabytes, so a copy's `src-tauri/` keeps no `target/`. Its dependencies are built once for all; the window's crate has units of its own per copy's folder (cargo keys a path package by its path). Cargo dates an input by its mtime, which the sync carries from the Mac, so a folder synced again with a different file dated before its last build was served that build: `tauri_inputs_dated` (`bench-env.sh`) touches the crate's inputs, `bridged.ts` included, when their content moved since the folder's last build, its stamps in `tauri-target/.inputs/`. The window a Tauri session opens is the copy's own, `.artifacts/station-window`, taken under a lock as it is built: `debug/station-window` is whichever copy built last.
- In the copy: `node_modules/` and the window's artifacts folder (the bench's logs, the proof build, the captures, `go/`, the copy's Go caches). The Tauri scripts remove `src-tauri/gen` and `src-tauri/Cargo.lock` when they end, and no Python run writes `__pycache__`.
- In the temp folder: nothing; every world session (`window-world-*`) and seed (`window-seed-*`) is removed when its process exits, by its end, an exception or SIGTERM (`world.py`, `temporary`); a SIGKILL alone leaves one.
