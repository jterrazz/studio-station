# ADR-034: Apply carries a Machinefile; the ledger bounds removal

**Status:** Accepted
**Date:** 2026-11-11

## Context

[ADR-033](033-a-machine-is-declared-by-its-machinefile.md) declared what a machine carries and resolved it into steps, but nothing carried them out: `init` ends on an empty state ([ADR-030](030-init-makes-a-machine-known-apply-carries-its-machinefile.md)), no machine recorded which Machinefile it carries, and nothing could tell what station had installed from what the owner had, so no removal could be safe.

## Decision

- **The binding.** A machine carries one Machinefile, recorded in `preferences.json`'s `machinefile` group as `name`, beside the shared source. `station init --machinefile <name|path>` and `station apply --machinefile <name|path>` bind it; `plan`, `apply`, `drift` and `explain` with no Machinefile named read the bound one, else the one named after the machine.
- **A path is copied, never referenced.** A Machinefile named by its file is copied into the owner's folder, `~/.config/station/machinefiles/<name>.yaml`, under the name it says, and the machine is bound to that name. Every later read finds it in the user layer like any of the owner's files: a file in a download folder can go away, every read has one place to look, and `extends` and the overlay keep resolving by name. `plan --machinefile <path>` reads the file in place and copies nothing.
- **The copy never replaces the owner's file.** The same bytes copy nothing; other bytes under a name the folder already holds are refused before any effect, with the hint to edit that file or remove it. Refused rather than asked on a terminal: the file the owner keeps is the one station never rewrites (the Machinefile is the owner's, station only reads it), a question would put that rule to a keystroke, and a refusal reads the same on a terminal and off one.
- **plan, apply, drift.** `plan` reads each item through its family (apps' inventory, settings' judge, by their calls) and says, first, what it asks of the owner, once per need, then what it installs, sets, adopts and leaves, what is extra, and what has to happen once applied, each once. `drift` is the same read as conditions (present, absent, outdated, changed, not managed, extra, unknown), and never acts. `apply` carries the plan out one item at a time by `apps.install` and `settings.apply`: a failure fails only the items that wait on it, an interruption stops the run and says `station apply resumes`, an item present by another way is adopted and never installed again, a setting changed by hand is left as it is, and off a terminal a plan that asks anything (a password, a license, a question) is refused before any effect. A `vault:` value is read from the vault only to hand it to its setting, and the run's words never carry it.
- **A password is the machine's answer.** A sudo need asks the owner only where this machine's sudo asks a password, which a plan that holds one reads once, before any effect, through the `machinefile` family's `Password` contract: `sudo -k -n true`, which never prompts (Touch ID included), ignores a password typed minutes before and runs nothing but `true`, within 5 seconds. The machine answers, never its kind: an owner's Mac can have a passwordless sudo and a VM can lose its own, and a read that cannot tell counts as asking, so a run off a terminal is refused as it was. A Linux VM station builds gives its admin a passwordless sudo (`src/catalog/images/linux.sh`), so its plan asks no password; the macOS image is fetched, with no recipe of station's, and is passwordless only as its base made it. It is the one sudo station runs on the owner's Mac outside the planned restart, and it elevates nothing the owner did not already allow without a password.
- **The ledger bounds removal.** `~/.local/state/station/ledger.json` (a store of the `machinefile` family, with its Migrator) records each app `apply` installed, its method and the Machinefile that listed it; what finished just before an interruption is recorded too, by the method that holds it, when its install handed back nothing, once a fresh read of the apps (every method listed again) gives that item's row within 15 seconds of the interrupt; one whose read does not answer by then stays unrecorded, which only keeps it from any removal. Two applies at once take its lock in turn (an exclusive `flock` on `ledger.json.lock`, held for one record, so the second waits milliseconds rather than being refused), and each change is written to a temporary file renamed over it. What the ledger holds for this Machinefile that it lists no longer is extra; an `optional` item it still lists, skipped on this system (no method here today), is listed all the same, and one recorded for another Machinefile is not this one's to take. What station did not install, adopted or present before, is never removed.
- **What `--remove` takes is what it reads.** An extra is uninstalled while it reads there by the method the ledger names, whoever put it there last (one reinstalled by hand by that same method is taken back too), and never by its name alone: one held by another method since is the owner's and kept. One station cannot uninstall (a script's install, the App Store's) is judged so by the plan: never removed, never asking anything (no password for an uninstall that cannot run), `station cannot uninstall it: kept, and yours: remove it by hand if you want`. One already gone, one held by another method, and one station cannot uninstall that nothing needs are said and forgotten by the ledger, so no later run fails on it, in the same words in the plan and in the run (`kept, and yours`), and a plan that holds one is not calm: `apply --remove` would change the ledger, so the plan ends on its hint; one whose manager is missing here, whatever it reads (it cannot be read by its method, nor uninstalled by it, so absent proves nothing) and a read that did not answer keep their record for the next run. The extras run dependents first, what they lean on (what they require, their provider, their manager) after them, and an extra another app there still needs (it leans on it by a link the resolution follows: it requires it, provides it, or manages it) is kept with its record while that app is not taken back with it, whoever installed it: removing it would break an app the owner kept. That app is judged by its method as the apps' inventory reads it (the one chosen here, even when it is present another way); an app the inventory holds no row of is not for this machine, and a setting's requirement keeps no app. An extra station cannot uninstall is never counted as taken back, so what it leans on is kept with its record, and what needs it is said too (`required by <app>: kept`), its own record kept; one whose uninstall fails at the run stays, and what it leans on is kept with its record. A manager station installed is never taken back while it holds packages of the owner's: what each method it manages lists that no app of the catalog placed here installs by that method (node's npm and corepack being its own), since uninstalling it would delete them; that list is read as every command station runs for apps is, from the owner's home, in an environment station builds rather than the shell's (mise's shims first on its PATH and no runtime's own folder there, mise's profile, a version named in the environment and npm's prefix left out), with mise pinned to its global file and its auto-install off, and npm's list names the folder of each node mise holds globally (`--prefix`, once per installed version of the global file), as its removal does, so it covers every node `mise unuse --global node` would take back, wherever station was started and whatever PATH it was given, and the read installs nothing; one whose list does not read may hold them, so it is kept too, `holds <n> packages of yours: kept` (`what it holds does not read: kept`), with its record, and it is taken back by the run after it holds none. What an uninstall asks (a package's password) is judged with the plan's needs, before any effect: off a terminal, `apply --remove --yes` with such a need is refused before any install.

## Consequences

- `apply` crosses families only through their calls, so the gates, the confirmation and the words of `apps.install` and `settings.apply` are those of the commands the owner already runs.
- An app the owner installs by `station apps install` is not in the ledger, so `apply --remove` never takes it; only the Machinefile's own installs are station's to take back.
- Settings are not in the ledger: settings keep their own record of what station applied, and turning one off stays `station settings off`.
- `plan`, `apply` and `drift` refuse a Machinefile as `explain` does, through the same resolution; its refusals are proved once, under `explain`.
- Accounts and ports are not read by the plan yet: the ports' rights are their own lot, and the accounts a computer keeps are only shown by `explain`.
