# ADR-040: apt takes back only what it names; a release installs only what a checksum vouches for

**Status:** Proposed
**Date:** 2026-11-11

## Context

[ADR-038](038-an-app-is-carried-by-one-method-the-one-its-plan-shows.md) chose an app's method by one order, and left `apt` and `github-release` unchosen until their installers landed. The design ("Managers: one responsibility each") makes apt the system manager of the debian family and github-release the last resort for a command no system manager ships, ranked `ubuntu: [apt, github-release, script]` and `macos: [brew, cask, mas, github-release, script]`. Both run code on the machine: apt as root, a release as a binary downloaded from the internet. [ADR-034](034-apply-carries-a-machinefile-the-ledger-bounds-removal.md) bounds what a removal may take back to what the plan read, and asks a password only where this machine's sudo asks one.

## Decision

- **A name that reaches root or a path is one name, by one rule.** A package, a pinned version, a command, a repo and a release tag each have one rule, the catalog's (`CheckPackage`, `CheckPackageVersion`, `CheckCommand`, `CheckRepo`, `CheckTag` in `src/catalog/names.go`): a package is Debian's (`[a-z0-9][a-z0-9+.-]+`, an `:arch` at most), a command one path segment (no `/`, never `.` nor `..`, never opening with `-`), a repo `owner/name` with no `..`, a tag one segment of the API route (letters, digits and `._+~-`, no `..`, no `/`, `?`, `#` nor space, never opening with `-`), checked before the route is built. The decoder refuses an item that breaks one, and every installer checks the rule again where it builds an argv or a path, since an install also crosses the wire from a peer and a record is read back from the disk.
- **apt changes the machine as root, asking nothing.** Every install, update and removal is `sudo env DEBIAN_FRONTEND=noninteractive apt-get -y`, keeping a configuration file the owner changed (`--force-confdef --force-confold`); off a terminal it is `sudo -n`, so a sudo that would ask fails rather than wait. An apt method must say `needs: [sudo]` (the decoder refuses one that does not), so a Machinefile's plan asks the password once, through ADR-034's read, where this machine asks one. Each install and update refreshes the lists first. Every argv ends apt's options with `--` before the packages, so a name is never read as an option, and every read of apt's runs with `LC_ALL=C`, since station parses its words.
- **apt's removal takes back what it names, and nothing it would widen to.** apt removes every package that depends on one it removes, so `apt-get -s remove` is read first and a removal whose simulation lists any other package is refused before anything runs; autoremove never runs (`APT::Get::AutomaticRemove=false`), so what a package alone pulled in stays. An app of several packages is held only while all of them are, its install records each package it added (`~/.local/share/station/apt/<package>`, naming the apps that hold it), and a removal takes back only the packages recorded, each with the last app that holds it: one the owner had before stays, the app's own package included, and one another app holds stays while that app does. An app none of whose packages is recorded is the owner's, and its removal takes its first package alone.
- **apt is read by dpkg.** A package is held when dpkg says it is installed (`ii`), behind when `apt-cache policy` gives another candidate. A version asked pins the first package of the method (`<package>=<version>`). The `apt` manager item is installed by apt itself (the `apt` package), so on Ubuntu it reads held.
- **A release installs only what a checksum vouches for.** Station itself fetches the release through the GitHub API, never a script and never as root: the one asset matching the method's pattern is read whole and hashed, then checked against every checksum the release gives it, GitHub's digest of the asset and the line naming it in a checksums file. One that differs refuses it; none at all refuses it too, unless the method says why it is `unverified`. Nothing is written before that check.
- **A release lands in the owner's search path, and only over station's own files.** The commands go to `~/.local/bin`, each by a rename over its old file of a file written anew (a link left at that name is removed, never followed); `~/.local/share/station/releases/<owner>/<name>.json` records each by the hash of the file written, before they land and once they did. A command there that is not station's file is the owner's: never overwritten, never removed. The inventory holds a release at the tag whose files are in place, so an interruption between two commands holds none, and the next install mends it. A record is checked as an install is (a repo whose record is that very file, commands only); one that breaks the rule, or does not read, holds nothing, and the others are read all the same. A command is the runnable file of the asset by its name; a lone compressed file is no command.
- **Station is the github-release manager.** The `github-release` item manages that key, ranked `macos: 3`, `ubuntu: 2`, `debian: 2`, after each system's own managers. Its method is station's own release, and the running binary is held (its version is `station --version`'s) by whichever installer of releases runs (a machine's, a world's fake, through one wrapper, `githubrelease.Own`), always current, never installed, updated nor removed by it: station's own update stays its install line.
- **An update waiting of a manager v3.0 lacks updates nothing there.** The fix of an update waiting always carries `method`: v3.0's word where it has one, else the manager's own key, which a v3.0 menu bar matches to no app, so its Update all updates none rather than every app.

## Consequences

- No built-in item installs by apt or by a release yet: L3.3 moves the Linux methods off mise onto them. Their argv is proved in `specs/adapters/apt/` and `specs/adapters/githubrelease/`; the release invariant has one enumeration test over every path an install takes (`src/apps/adapter/githubrelease/githubrelease_test.go`: fresh, pinned, upgrade, re-run, interrupted at each write then run again, a wrong checksum, a wrong digest, another arch's asset under this one's name, none, no asset for this arch, another arch).
- A checksum from the release vouches that the bytes are the release's, not who built them: a release whose author is compromised passes. Signatures (sigstore, GPG) are not read.
- An asset is read in memory through the 30-second HTTP budget every station GET has, and cut at 512 MiB as every answer is, so a large asset on a slow link fails; the small CLIs of the catalog fit. Of an archive, only the files a command names are kept in memory (512 MiB each), and the archive is read through to 2 GiB at most.
- A Linux computer runs apt with a password only on a terminal; a VM station builds is passwordless, so its plan asks nothing.
- An apps list this station sends a v3.0 reader fails to decode there whole once it names an `apt` or a `github-release` install: v3.0's `installOf` has no case for either (`git show v3.0.0:src/catalog/liveson_wire.go`), the same as for `provided-by` since 3.1.0. No built-in item installs by either before L3.3; the older-words pass of the next minor carries them, with `provided-by`.
- Held packages, dpkg's lock timeout, two installs at once, GitHub's API rate and a checksums file that names the asset twice are left for later (`TODO.md`, the L3.2 security verify's F6, F8, F9 and F10).
