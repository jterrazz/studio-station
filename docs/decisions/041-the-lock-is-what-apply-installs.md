# ADR-041: The lock is what apply installs; upgrade alone moves it

**Status:** Accepted
**Date:** 2026-11-11

## Context

A Machinefile says what a machine carries, never which version or which of an app's methods holds it here ([ADR-033](033-a-machine-is-declared-by-its-machinefile.md)). Two machines applied from one Machinefile a month apart got different versions, a catalog whose priorities changed between two stations chose another method for an app not there yet, and nothing kept a shared source's commit beside what it had installed: a `preferences.json` pin moved by any hand ran the new source's scripts at the next `apply` ([ADR-034](034-apply-carries-a-machinefile-the-ledger-bounds-removal.md) bounds removal, not what an install takes). The design asked for `machinefile.lock` (each item's resolved version and the manager that installed it, plus the shared source's commit) and `station upgrade` (station, then the managers, then the items), and left open where the lock lives, what it holds on each path, and how it meets a Machinefile that changed since.

## Decision

Superseded in part by [the versions ADR](044-versions-are-semver-ranges-applied-nightly.md): a `version` is a semver range an app moves within, no longer a prefix the lock meets (`22` met by `22.11.0`) nor a pin `upgrade` keeps; the shared source's commit pins nothing and `machinefile.source-moved` is gone, the source following its default branch forward; and the last consequence's open question is settled, `upgrade` fetching the branch's newest commit.

- **Where.** One lock per Machinefile on each machine, `~/.config/station/machinefiles/<name>.lock` beside it, in the schema `station.lock/v1`, read as strictly as a Machinefile. No source reads it (a source reads `.yaml` alone), so a lock is never a layer of anyone's catalog. A lock that does not decode is refused at its file with the way back: removing it, since the next `apply` writes it anew from what is there. It is station's file, written whole by a rename, its apps by name, so the diff of two locks is what moved. A run writes only its own move, from the lock it planned from to the one it ends with, applied to the lock as it stands under a file lock (`.writing`, beside it, with a temp name of its own), so two runs at once keep each other's lines.
- **What it holds.** The Machinefile's name, the shared source's name and commit the run read, and each app (managers included) with the method that holds it and the version that method lists. Settings carry no version and are not locked.
- **The invariant.** What `apply` installs is what the lock names, on every path: fresh (no lock: the resolution's choice, then the lock written), locked (an app the lock holds is installed by the lock's method, at its version where that method pins one), upgraded, interrupted (what finished before the interrupt is locked, what did not keeps its line), adopted (locked by the method that holds it), and from another kind of machine (a lock whose method this one has not gives way to this machine's choice, written anew). After every run the lock names, for every listed app that reads there by a method, that method and the version it reads; an app the run did not bring there keeps its line, so the next `apply` installs it as locked; a copy no method holds is the owner's and leaves the lock, as does an app no longer listed. The enumeration test is `src/wire/lock_test.go`, over the fake world, for every app of the catalog on every kind of machine; the model's own every way a line ends is `src/machinefile/lock_test.go`.
- **The lock chooses inside what the Machinefile allows.** It is an input of the resolution, after the selector and an entry's `manager`, before the system's order: its method wins when it is one of the matching methods, its version where that method pins one and meets the version asked (`22` is met by `22.11.0`, `220.1` is not). A Machinefile changed since (another `manager`, a version the lock does not meet) wins, and the run writes the lock anew. `explain` names the lock as the layer of the method it chose (`lock`), the plan the version it installs (`locked 3.12.7`), and only where the method pins: for a method that cannot (brew) it shows the version the lock records (`recorded 14.0.0`), never claiming it is installed.
- **A version station cannot pin is recorded, not enforced.** brew installs a formula's newest; its lock line is what the run read, and a second machine applied from it may hold a newer one. Pinning exists where the install carries a version ([ADR-038](038-an-app-is-carried-by-one-method-the-one-its-plan-shows.md)).
- **The shared source's commit.** A lock written from a shared source holds its commit, and a run that is not `upgrade` reads only that commit: `apply` refuses a source pinned at another one since, or dropped, before any effect (`machinefile.source-moved`). `upgrade` takes it and writes it into the lock. Moving the pin itself stays the owner's gesture in `preferences.json`.
- **upgrade.** `station upgrade` (`machinefile.upgrade`) updates every listed app that reads there by one of its methods, by that method (`apps.update`), the managers first and then the rest, each in the plan's order. A version the Machinefile pins is kept; a copy no method holds, an app of another phase and an app not there are left, but for an app the lock holds that is not there: its locked version may be what can no longer install, so apply's failure names `station upgrade`, which installs it by the lock's method at the newest the Machinefile allows and relocks it. It then writes the lock anew and returns what moved. An update caught by an interrupt is read again past it, as apply's install is: one that reads there at another version finished, and the lock takes it. Off a terminal an upgrade whose updates ask anything is refused before any effect, as `apply` is. Homebrew's index is refreshed by homebrew's own `upgrade:` line (`brew update`), since every bundle station runs carries `HOMEBREW_NO_AUTO_UPDATE=1`: an install during `apply` never moves a formula the owner did not ask for.
- **station itself is not upgraded here.** The plan's first step of `upgrade` (the release asset with its checksum, replaced by a rename, the engine restarted on the new version) is not in this decision: re-running the install remains station's own upgrade ([Release](../guides/release.md#how-a-machine-takes-it)).

## Consequences

- A lock copied from one machine to another of its kind reproduces its methods, and its versions where they pin; a lock of another kind is harmless, rewritten for this one.
- A lock never blocks an `apply`: a line it cannot honour gives way and is rewritten, and only a moved shared source or an unreadable lock stops the run, both before any effect.
- The lock beside a template in the shared source (`studio-linux.lock`, committed, so every image bakes the same versions) and an image built from a lock wait for `images build <machinefile>`, which reads it; this decision writes and reads the machine's own.
- station's self-upgrade, and whether `upgrade` also fetches the shared source's newest commit rather than taking the pin the owner moved, are open (TODO).
