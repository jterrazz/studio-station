# Testing

Three tiers prove station, each with one purpose, and a fourth rig runs the menu bar's gate where this Mac has no Xcode. Tier 1 is `make check`: the Go tests (the architecture rules, the contract suites, the few module tests a spec cannot reach), the use-case stories over a fake world, the adapter documents against stub programs, and the menu bar's stories, every state of its panel drawn against its goldens. Tiers 2 and 3 run the real binary on real VMs of this Mac, outside the gate. Every use case of the product is proved by a story in the owner's words, and a test exists only because a real regression would turn it red.

## The two suites

```sh
make test      # go test ./src/... ./specs/..., then typescript test: the specs against a fresh build of station, then the machines and engine/keep use cases again over vz
npm test       # the specs alone
```

The Go tests come first. The module tests are `*_test.go` files next to the code they judge, kept only for what no session of the binary reaches honestly: a state the terminal driver cannot observe (the TUI loading in `Init`, a busy screen, the renderer's colours), a timing budget, root, a pure algorithm whose edge cases are cheaper at its own level (the renderer goldens: every page fixture of `src/ui/testdata/pages/`, written by `make generate` from the real page functions, rendered by every renderer of `src/ui/render/` and compared with its file in `src/ui/testdata/__expected__/`; `go test ./src/ui/... -update` rewrites them). The architecture test, `specs/architecture/`, proves each of its rules still bites by judging one violating file in memory; its rules are [Architecture](../concepts/architecture.md#who-may-import-whom)'s. Each contract's suite, `src/<family>/contract/contracttest/`, runs against its real adapter (over `platform/local/localtest`'s scripted door) and its fake alike, so a fake cannot drift from what it stands for.

Then `make test` runs the CLI specs under `specs/cli/` on Vitest, through `@jterrazz/test`. There is exactly one runner, and every spec drives one binary, `.artifacts/go/station-test`, stamped with the version `git describe` prints: the spec build (`-tags world`), which runs the real adapters unless a document hands it a world ([below](#a-use-case-over-a-world)). `make test` builds it once before the runner starts, so no worker links it while another drives a session (with one build per worker, nine links ran beside the first sessions), and tells the runner so (`STATION_SPEC_BUILT=1`): a gate runs that one binary to its end, even when `src/` changes under it, rather than documents rebuilding it in every worker and half the run testing other code. Run directly, `specs/cli/cli.specification.ts` rebuilds it when it is missing or when any file under `src/` is newer than it, beside the binary and renamed into its own file, so a worker never executes a half-written file. It is an mtime check, so editing the CLI and re-running the suite always exercises the change instead of a stale build.

`vitest.config.ts` is the one line `@jterrazz/test` derives from `studio.config.ts`: its `cli` project collects `specs/cli/`, `specs/adapters/`, `specs/usecases/` and `specs/tui/` (one screen of the TUI over a world), and every `*.spec.yaml` there becomes a one-test module driving that runner. A document of `specs/adapters/<tech>/` proves one adapter speaks its program (its argv, its parsing, against the stub CLIs a fixture carries): `.calls` assertions belong there, and nowhere else once a family has moved. The runner's defaults are [the fenced run](#the-fenced-run).

## A scenario is a document

Almost every spec here is a terminal session (a command, its exit code, what it printed), so it is written as one: a `<case>.spec.yaml` in the command's folder, in the literate format of `@jterrazz/test`. The file IS the test; `description:` is its title in the runner, and each entry of `runs:` states the command, its `exit:` and its `stdout:`/`stderr:` byte-exact.

```yaml
# specs/cli/root/unknown-command.spec.yaml
description: an unknown command is one error block on stderr, without colour, and exits 2
runs:
    - command: nope
      exit: 2
      stderr: |
          Error: unknown command "nope" for "station"
          Hint: run station --help
```

A document may stand on ground of its own: `fixture: ./__fixtures__/<case>/` spreads that folder into the working directory, which is the run's `HOME`, so a stub program under its `bin/` answers the binary. Ground sits in a special folder spelt with double underscores; a subject folder never starts with one. Where a stream is long and only some of it is the claim, the command writes it to a file (`help > help.txt`) and `files:` asserts what it `contains`.

`TEST_UPDATE=1 npm test` rewrites the `exit:` and the streams of every document from what the binary actually printed: deliberately, after a change to a command's output, and never as a way to make a red suite go green. Nothing else in the file is touched.

## The fenced run

No spec reaches the real machine. The runner sets `HOME` to the run's working directory and unsets the variables that would move its folders, name a credential or describe the owner's terminal (`XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, `GOENV`, `MISE_CONFIG_DIR`, `MISE_DATA_DIR`, `MISE_GLOBAL_CONFIG_FILE`, `GH_TOKEN`, `GITHUB_TOKEN`, `TERM`, `TERM_PROGRAM`, `COLORTERM`) unless a document states them, since GitHub's Ubuntu runners export `XDG_CONFIG_HOME` and every run would then share one folder of preferences; the `terminal` env names the TUI's terminal `xterm-256color` with `COLORTERM=truecolor`. It sets `PATH` to its `bin/` alone (the fixture's stubs), and `STATION_SYSTEM_DIRS` to nothing, so a system program no fixture stubs is "not found" alike on a Mac and on the Linux CI runner (the manager folders the binary adds to its own search, `/opt/homebrew/bin` and `/usr/local/bin`, are read under that root too, so a fixture's installer lands a manager in `root/opt/homebrew/bin` and never meets the owner's), and `STATION_SYSTEM_ROOT` to the run's `root/`, so `/Applications`, `/opt/homebrew` and `/Library` are read there and the owner's own apps are neither listed nor sized; the free space is that of the volume holding `root/System/Volumes/Data`, or the nearest of its folders that exists. `STATION_POWER_STUB` points the IOKit contract at the run's stub folder (a fixture writes one): its files are the reading, every assertion and clamshell call is a line of `.calls`, and with no such folder the run has no IOKit contract at all, so no spec takes a real assertion. `STATION_KERNEL_STUB` points a Mac's counters and process tables at the run's `kernel/` folder, recorded kernel tables (`counters.json`, and `procs.json`, the process tables successive reads walk through), and with no such folder the kernel answers nothing, so no spec reads the real machine's activity. It also pins `NO_COLOR=1`, `COLUMNS=80`, `TZ=UTC` and `STATION_MACHINE_KIND=mac`, so every stream is the pipe form and a document means the same thing on every machine: the pinned kind also picks the adapter the machine reads itself with, so a Linux runner reads a pinned Mac as a Mac. A fixture's script holds to the same rule: it calls what a Mac and an Ubuntu runner answer alike (`perl` for a date, a crop by character or a unix socket, `ls -l` for a mode), never a BSD-only or GNU-only flag.

## A use case over a world

A document of `specs/usecases/<family>/<verb>/<outcome>.spec.yaml` tells one outcome of one call (`machines/stop` is `machines.stop`; `engine/<job>` is an engine job; `root/`, `remote/`, `output/`, `errors/`, `migrate/` and `security/` hold what spans calls) against a seeded fake world, and asserts what the owner reads, never an argv. It names its world as an env set, `env: two-macs`: the runner registers one per file of `specs/usecases/worlds/`, which points `$STATION_WORLD` at `world.json` in the run's directory and seeds it from that file at the first run. Every run then reads and writes that one world, so a document can say what the world became by reading it back through the CLI.

A story reads as the owner's session: commands, what they printed, then a world event and what the owner reads after it.

```yaml
# specs/usecases/machines/stop/server-confirmed-stays-stopped.spec.yaml (shortened)
description: "a server stopped with its name typed wants to stay stopped: its Mac's reboot does not start it"
env: [two-macs, terminal]
runs:
    - command: '... machines stop infra --on mac-mini --confirm=infra'
      stdout: |
          On mac-mini:
          ✓ infra · stopped · wanted state: Stopped
    - command: 'world reboot jterrazz-mac-mini'
    - command: 'machines --on jterrazz-mac-mini'
      stdout: |
          ○	infra	Server	jterrazz-mac-mini	Stopped · always on	8 CPU	24 GB
```

The worlds are the files of `specs/usecases/worlds/` (`two-macs`, `one-mac`, `mini-offline`, `in-workspace`, `in-server`, `on-battery`, `serve-off`...), each the ground of many stories. A world event is the hidden `station world <event> [args]` of the spec build, from the closed list of `src/world/events.go`: a Mac's `reboot`, `power-cut`, `unlock`, `offline` and `online`, `engine-crash`; a VM's `crash`, `poweroff-inside`, `reboot-inside`, `console` (a line its console writes), `address`; `listen` and `unlisten` a port, `container-run`; `edit` a file by hand; `unplug`, `plug`, `close-lid`, `open-lid`, `will-sleep`, `thermal`, `battery`, `low-power`; `advance` the clock; `fault` and `hold` a contract's method; `upgrade` a Mac's station; `slow`; `reads` a fact; `unopened`, an app never opened on a Mac, so a command it brings at its first launch is absent; `certificate`; and an agent's hook firing inside a VM, `agent-prompt`, `agent-step` (a step, its output a PR's URL opening the PR), `agent-notify`, `agent-stop` and `agent-end`, each folded into that VM's journal. An event changes only the world; what station does about it is what the next command shows.

The world (`src/world`) holds what is outside station, one slice per family: the repositories a shared source is read from, at each commit; each Mac's engine (its job, when it started and when the owner stopped it), the station it runs (an older version, and the calls it `lacks` until `world upgrade`), preferences, the files a store has not read yet (a hand edit, a file station v2 left), the owner's item files and Machinefiles (`world edit <mac> machinefiles/<name>.yaml`) and station's other stores, its Self, its battery and lid reading, what listens on it, its tailnet node, its installers, meter (its counters, and how much each grows a second on the world's clock), disk, jobs, vault, facts and ssh config, its images and VMs (what station keeps of a VM, beside its disk, its run and when it began and ended on the world's clock, its guest and what listens in it), and the faults scripted for the fakes. Under `$STATION_WORLD` the spec build wires every family's `adapter/fake` over its Mac's slice instead of the real adapters (`src/wire/world_on.go`, the one file that knows the tag; `release_test.go` fails when a family's fake is not linked), runs each Mac's engine inside the command, stepped over the world's clock until it is quiet (the clock moves only for the command that waits, a tick and an advance: what the engine runs in its own lifetime waits for it), and reaches another Mac of the world in-process, through the wire form. A world event is a run of the hidden `world` command, `command: 'world reboot jterrazz-mac-mini'`; its closed list is `events()` in `src/world/events.go`; an event no fake models yet is refused as such. `world edit <machine> <file>` gives a file of station the text on its stdin, as a hand edit would. `world fault Hypervisor.Boot [2 times]` fails that contract's method the next calls (every call, without a count) in the fakes that obey it: `Hypervisor.Boot`, `Installer.<verb>`, `Bundler.Bundle`, `Jobs.Install`, `Jobs.Start`, `Listeners.Read` (what listens on a Mac cannot be read, so its ports read fails), `Tailnet.Share`, `Unlocker.PlannedRestart`, `CheckRunner.Run`, a server's check that stops answering, `Meter.Sample`, a Meter that does not answer, and `EndpointDialer.Dial`, a Mac whose ssh answers with no station there. `world hold <Contract>.<Method>` makes the next call of that method wait until it is interrupted (`Installer.<verb>` and `Bundler.Bundle` after their first item, `Hypervisor.Clone`, `Hypervisor.Boot`; `Unlocker.PlannedRestart` is a restart that never comes back). A held hypervisor call first writes its run's world back and lets go of it, so the `run` step of a terminal document reads, with a command of its own, what the held create has made so far (`machines/list/creating-while-cloning`).

A second hypervisor must pass the VM use cases unchanged (AR-02), so `make test` runs `specs/usecases/machines/` and `specs/usecases/engine/keep/` a second time with `STATION_SPEC_HYPERVISOR=vz`: the runner then sets `$STATION_WORLD_HYPERVISOR` in every world, and each Mac that had station's own hypervisor runs the fake `vz` instead (a Mac whose world says `"hypervisor": "none"` keeps none). The env set `two-macs-vz` is two-macs over vz for a document that names it.

`specs/architecture/coverage_test.go` reads the registry and walks `specs/usecases/`: every call needs a story of each outcome it declares (done, each code it may end in, `not-for-this-machine-<machine>` for each reference machine its rule refuses, `on-another-machine` when it is routable), and a document names only a real call and outcome. The calls not covered yet are its allowlist, which only shrinks. `release_test.go` proves the release binary links no world and no fake.

## The TUI on a terminal

A run is never given a terminal, so a document that needs one names the `terminal` env set and runs `--version >/dev/null; terminal "$STATION" [words]`. The `terminal` stub of `specs/__fixtures__/terminal/`, which any noun's document lists in its `fixture:`, opens a pseudo-terminal (80x24, or `--size`), replays what the binary draws on a screen of cells, and plays the steps the document writes on `stdin:`: `see` and `gone` wait for a text on the screen (10 s; `within SECONDS see TEXT` bounds the wait, so a document can say a row appeared before a slow read ended), `file PATH` waits for a stub to have written PATH, so a step can follow a read's start, `run COMMAND` runs a shell command beside the binary and fails unless it exits 0 (a world event while a screen is shown, or a look at what a key changed: the TUI's own process writes no world back, its children do, but for the watch it holds while it shows a machine's activity, the engine's `watching`), `send` types keys (`\r`, `\x1b[B`), `settle` waits until the binary has drawn nothing for 0.2 s (1 s at most), so the next key reaches the frame the last one drew, `clipboard TEXT` waits for the binary to set the clipboard to TEXT (OSC 52), which also lands in `./clipboard` for a `run` step to read, `screen` prints the screen, and `scrollback` waits for the binary to exit and prints the history above the screen with the screen, as tmux keeps it (a clear from the screen's first cell joins the history), so a document can count the copies a live read leaves; `asked` waits for it to exit too and prints how many times it asked the terminal for its background colour, which the screen answers as a dark terminal does. It then exits with the binary's code, and a wait that times out, or a `see`/`gone` the binary exits before, prints the screen, the bytes the binary drew and the seconds it ran on stderr and exits 124, so a binary that never started reads apart from a slow first frame; one the driver could not run at all (exit 127) prints why on that screen, the call that failed and its errno. The screen is a terminal with synchronized output, as the ones the TUI runs in are: the TUI brackets each frame, and a step reads the last frame drawn whole, never one half drawn. The size is set before the binary starts, so its first frame never races the driver for it. The TUI's own sessions are the documents of `specs/tui/`, one folder per screen; one whose gesture opens something lists `specs/tui/__fixtures__/opener/` too, whose `open` and `osascript` stubs open nothing and record each call in `$HOME/opened`, one line each (`open x-apple.systempreferences:…`), which a later run reads back. The `terminal-*.spec.yaml` documents of `specs/cli/root/` are the TUI sessions of the root command; `init`, the `config` items that ask values, the confirm gate of a destructive verb and `machines unlock` drive the binary the same way.

The full grammar is `@jterrazz/test`'s [Spec documents](https://github.com/jterrazz/package-test/blob/main/docs/guides/spec-documents.md) and [CLI specs](https://github.com/jterrazz/package-test/blob/main/docs/guides/cli-specs.md).

## The stubs

A spec copies one `fixture:` directory into its working directory, so stubs live beside the command word that uses them: `specs/cli/<noun>/__fixtures__/<case>/bin/<tool>`. A fixture both suites read (the VMs `vms/`, the running VM `engine-vm/`, what Tailscale serves `serving/`, the two Tailscale apps) lives in `specs/__fixtures__/`, the lowest folder `specs/cli/` and `specs/adapters/` share. A stub answers by argv from a table, appends `<tool> <argv>` (and the stdin of `brew bundle --file=-`) to `$HOME/.calls`, and exits 97 on anything unscripted. A document asserts `.calls` through `files:` to prove which installer line ran. The GitHub API is a stub backend the runner serves, reached through `STATION_GITHUB_API_URL`; a VM's sshd is the stub `vm-sshd` (`specs/cli/__fixtures__/vm-sshd/`), served to the documents that declare `serve: sshd` and reached through `STATION_GUEST_SSH_PORT`.

## The menu bar's stories

The menu bar is proved by its stories ([ADR-026](../decisions/026-the-stories-are-the-menu-bars-test-suite.md)): every state of its panel is a story, an id of `apps/menubar/stories/STORIES.md` (its section is its group) with its `<id>.story.json` beside it, in `station.story/v1`: its `group`, a `note`, the `pages` it draws (files of `stories/pages/`, which `make generate` writes from the real page functions over the story worlds of `src/cmd/generate/pages/stories_<group>.go`), the panel's state over them in `ui` (a segment, an unfolded section, a sheet, an alert, a menu, a popover, a Find query, a highlight), `samples` for its live values, `play` and `freeze` for a movement caught mid-flight, `tags` (`a11y`), and a `heightNote` when it is not as tall as the prototype's panel. `make menubar-check` runs them, as part of `make check`:

| Test                 | Fails when                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `StoryTests`         | a story's drawing, offscreen at 2×, still, over a flat desk, differs from its dark or light golden by more than 0.1 % of its pixels; it is not glass (40 % opaque or more, sheets and alerts aside); it is more than 4 pt from its height in `testdata/stories/heights.json` and names no `heightNote`; a group has no `a11y` story proved at Increase Contrast and Reduce Transparency; a transition is not caught mid-flight; the goldens pass their budget |
| `StoryCoverageTests` | an id of STORIES.md has no story file or no goldens; a story file or a golden names an id STORIES.md does not hold; `INDEX.md` or a story's Xcode preview drifts                                                                                                                                                                                                                                                                                              |
| `StoryLoadTests`     | a story file does not round-trip, names a page that is not there, or `Station.app` links the loader                                                                                                                                                                                                                                                                                                                                                           |
| `KitBoundaryTests`   | a view of the kit draws a size, a colour or a movement `Token` does not name, reaches for what the menu bar's window owns (a material, glass, `NSWindow`, `List`, `ProgressView`) or writes a glyph of the page's words itself; the Catalog draws other than through the kit, or `Station.app` carries it                                                                                                                                                     |
| `AppGlassTests`      | `Station.app` holds other than one `NSGlassEffectView`, sets the panel's content other than as that glass's `contentView`, or draws a second glass (`glassEffect`, a glass container, a material, `.containerBackground`, `NSVisualEffectView`) ([ADR-036](../decisions/036-the-menu-bar-owns-its-glass-panel.md))                                                                                                                                            |

The ids STORIES.md holds that no lot built yet are the coverage test's pending output, never a failure: the A2 additions it lists as `unbuilt` and the gap ids of STORIES.md's last section. Each list only shrinks: a story built leaves it.

To add a story: its section in STORIES.md (what it shows, the data it needs, its interactions); the world that holds its data, a `World` of its group's `stories_<group>.go`; `make generate`, which writes its pages, `INDEX.md` and its preview; its `<id>.story.json`; then its goldens, `specs/machine/menubar/run.sh <label> --update-goldens`, which rewrites every golden the menu bar VM draws and brings them back to `.artifacts/e2e/menubar-<label>/changes/` (look at each one changed before copying it into the tree and committing it). A failing golden leaves `<name>.actual.png` beside it in the stories folder of the kit's test data, which the next green run removes. To look without a test: `make catalog-export` draws every story (`FILTER=<regex>` a few) into `.artifacts/catalog/`, and `make catalog-gallery` adds the page to browse them on a phone ([Develop](develop.md)). `make catalog-open`, the Catalog's window, is the owner's gesture alone: no check and no agent opens a window.

## What a test is for

A test exists because a real regression would turn it red. Every behaviour of a command (each flag, refusal, exit code, `--json` schema and migration) has a spec document through the real binary; the architecture test proves the layers; a module test exists only where the logic is dense and a spec cannot reach it honestly (what the terminal driver cannot observe, a timing budget, root, a pure algorithm). A test that restates a declaration, a table or a mock's own return is deleted.

## The machine specs

Tiers 2 and 3 run the real binary on real VMs of this Mac, where the fenced run cannot reach: `make e2e-machine KIND=linux` (tier 2) and `make e2e-machine KIND=macos` (tier 3, one macOS VM at 8 GB: it refuses to start beside another running macOS VM, Apple running two at most, or without 8 GB free beside the running VMs, macOS keeping 4 GB; a running Linux VM is no obstacle), `LABEL=<label>` naming the log `.artifacts/e2e/<label>.log` (the kind by default). A Mac with no Go runs `specs/machine/run.sh linux|macos <label>` directly over the two binaries `make e2e-binaries` builds where Go is (a Linux workspace) and `scp` copies into `.artifacts/go/`. They live in `specs/machine/` (`run.sh`, the shared words of `harness.sh`, each tier's `<kind>/tier.sh`) and run only there: never in `make check` nor CI, since GitHub's macOS runners are VMs and nest none. Each case is a row of USE-CASES.md's `T2` and `T3` proofs: the log opens it with its name and use cases (`== case on-through-hop (MA-15 RM-20)`) and closes it with `PASS` or `FAIL`; an assertion a slow tier goes on past is a `MISS`, which fails its case and the tier; a `FAIL` inside a case ends that case only and the next one runs, while a failure of the setup before the first case aborts the tier. The verdict is the exit code.

Tier 2 runs the engine of this build (`station engine run`) for a Mac home of the run's own, `.artifacts/e2e/<label>/mac`: its PATH is its `~/.local/bin` and the system's, its IOKit contract the stub, its system root a folder of the run, and tart keeps its VMs in that home's `~/.local/share/station/vms`, the owner's OCI cache read through a link. The tailnet, the Mac's credential store and Claude's sign-in there are stubs (`specs/machine/linux/stubs/`), so the owner's Tailscale and keychain are never reached; what a VM receives is real. Its cases, in order: `image-build` (`images build linux --binary`, then a workspace whose station reports `workspace`), `create-workspace` (the health steps, ssh through `machines pipe`, the apps of `specs/machine/linux/one-per-method.txt` through the engine, the native commands, the footprint test of the workspace's home, `disk free`), `docker-shortcuts`, `claude-token-share` (the VM's credential store is a file-backed stub: how the studio CLI reaches a VM is not designed, so `claude` answering with a real token stays the owner's run), `activity-under-load` (`activity --on ws1` against the guest's `/proc`, idle and after a 1.5 GB `dd`, 400 MB the Mac sends it over ssh and two busy CPUs), `server-check-self-signed` (a server's check on its own name passes with the certificate its server made itself; the same check by address fails) and `on-through-hop` (a second home plays another Mac, reaching the first over a real ssh hop: this user's sshd on loopback, its sessions in the first home; `--on ws1` in BatchMode, then the owner's own `ssh ws1` through the block station wrote, before and after the VM takes a new address) and `rights-private` (ws1's Machinefile opens `3000-3999` to private: after a restart, 3000 is shared and served on the stub tailnet, 8443 is flagged and never reaches it).

Tier 3 clones a test-only image, `station-e2e-macos-<catalogue hash>`: the upstream `macos-tahoe-base` with Homebrew added by `specs/machine/macos/prebake.sh`, rebuilt only when `src/catalog/` changes. It is not a product image. Inside it the harness exports `STATION_MACHINE_KIND=mac`, so the guest plays a fresh Mac, and records what `kern.hv_vmm_present` prints there. Every VM it makes is named `station-e2e-*`, outside station's ownership rule, and deleted at the end, pass or fail. Its cases: `install-then-init` (`scripts/install.sh` through its one test seam, `STATION_INSTALL_FROM=<the binary just built>`, with `--name e2e` passed on to `init`, which runs neither `brew` nor `sudo` (both recorded on their way to the real ones, outside the home) and installs no engine, its steps and its empty Machinefile read back from a second `init`; then the apps of `specs/machine/macos/one-per-method.txt`, the native commands, then the footprint test), `shell-block-native-calls` (a login shell, `zsh -c` and IDE-like calls under `env -i` with only the app's own bin on PATH, plus `/usr/bin:/bin` for npm, whose launcher is `#!/usr/bin/env bash`), `apps-every-method` (each app of `specs/machine/macos/every-method.txt` installed, updated and removed; the App Store one refused signed out with its hint), `settings-every-one` (every Set by station setting applied, turned off and applied again, but those of `settings-asked.txt` and those a Mac refuses (`not-for-this-machine`); the checked ones against the system's own commands), `activity-in-macos-vm` (Activity read by a macOS workspace's guest: the CPU count and the memory size equal `hw.ncpu` and `hw.memsize`, no Thermal, no Battery; the binary is built without cgo, so its busy share and top processes are the cgo build's and not asserted), `disk-free-erase` `init-then-apply` (a clone of the raw base: `scripts/install.sh` with `--machinefile` of `specs/machine/macos/test-machinefile.yaml` (homebrew, jq, a cask, a setting) on a terminal, interrupted by `kill -INT` while the cask installs, then a bare `station apply` that finishes it, `station drift` with every item present, then the footprint test) and `bare-mac-homebrew` (a clone of the raw base, never this image, emptied of any Homebrew: one `apps install homebrew jq` installs it and bundles through it in the same process, then a second process finds it, so Homebrew's installer and its sudo ran once).

The menu bar's rig, `specs/machine/menubar/run.sh <label> [--update-goldens | --capture]`, is not a tier: it proves no product behaviour, only gives `make menubar-check` the Xcode this Mac does not have, and it is the reference that draws the menu bar's goldens. A golden drawn on a Mac is no longer the reference: the glass and the gradient of the desk differ between the owner's Mac's macOS and the VM's, layout and text do not, and `make check` on a Mac that has Xcode will report goldens as differing.

The rig clones the cached base `station-e2e-xcode-<hash of the image ref>`, made once from `ghcr.io/cirruslabs/macos-tahoe-xcode` pinned by digest in the script (the digest of the `27.2` tag: macOS 26.6.2, Xcode 27.2; `STATION_XCODE_IMAGE` picks another, and a new ref is a new base, the older one deleted). The base is kept like tier 3's image. It boots `station-e2e-menubar-<label>` headless at 8 GB (`STATION_VM_DISPLAY=<W>x<H>[pt|px]` sets the guest's display, which a headless guest otherwise lacks), pushes the committed branch into it by git over ssh, and runs `STATION_REQUIRE_MENUBAR=1 make menubar-check` there; `--update-goldens` adds `STATION_UPDATE_GOLDENS=1` and `STATION_UPDATE_INDEX=1`, so every golden and the stories' index are rewritten. The log is `.artifacts/e2e/menubar-<label>.log`; every file the run wrote under `apps/menubar` (an `.actual.png`, a rewritten golden) comes back to `.artifacts/e2e/menubar-<label>/changes/`, for the caller to copy into its tree. The VM and its disk are deleted by a trap, pass or fail, and the verdict is the exit code. Like tier 3 it runs one macOS VM alone.

`--capture` reads the live panel, which no golden can show, since a golden draws the glass's still stand-in. The run builds `Station.app` instead of the gate, boots the guest on a 1024 x 768 pt screen with Virtualization's VNC server (`--vnc-experimental`), and drives it from this Mac with `capture/drive.py` (vncdotool in `.artifacts/e2e/menubar-venv`, which the runs share). Nothing opens a window here, and the guest needs no Screen Recording grant. A fake engine, `capture/replay.py`, streams `home.exposed` to the app. `capture/wall.swift` draws the contrast round's three wallpapers (dark busy behind a white window, light busy, a colour gradient) where the panel opens. The driver clicks the status item at the frame the app logs, captures the screen and crops the panel to the window frame the app logs. `capture/measure.py` then finds every text of the golden by its tone, composites the token's colour over the glass pixels behind it, and keeps the WCAG ratio's 10th percentile. Its table and `<shot>.compare.png` (capture, M1's cell, golden) land in `.artifacts/e2e/menubar-<label>/capture/`. `STATION_CAPTURE_SET` picks the shots: `walls`, `behave` (the closing gestures) and `trial` (ADR-021's height and focus trial) by default, plus `sweep` (`STATION_TRIAL_TINT` from 0.5 to 0.9), `a11y` (Reduce Transparency, Increase Contrast) and `old`, a build that logs no frames, whose item frame `STATION_CAPTURE_ITEM=x,y,w,h` gives. `STATION_CAPTURE_M1=<dir>` names M1's scenes for the compare sheet.

The footprint test: the home is listed (depth 4) before the first step and after every step, and every new path must be one a Disk row holds (`station disk --json`) or [Footprint](../reference/footprint.md) declares, a home-root exception of Footprint, a path the OS writes itself (`specs/machine/<kind>/os-noise.txt`, never an app's), or one the suite's own native commands put where their user asked (`specs/machine/suite-made.txt`: `uv tool install` links into `~/.local/bin`). An unmatched path fails the suite, named with the step that made it. `station disk free` must leave every Can rebuild row empty and every Your data row untouched, and `station disk erase go --confirm=go`, on a fresh clone of the macOS VM, must take only go's data.

## What CI runs

`.github/workflows/check.yaml` calls the shared `studio-actions` check workflow on every push and every pull request to `main`; what that workflow runs against a repository's `make` targets is [The stack](../concepts/stack.md)'s. Locally the same gate is `make build` then `make check`.

The npm half is linted by the same toolchain as every other repository: `npm run lint` is `typescript check`, and `make lint` runs it after the Go half ([Develop](develop.md)).
