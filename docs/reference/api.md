# The API

`station.api/v2` is how every caller reaches a call on another process or another machine: the CLI reaches this Mac's engine with it, the menu bar does, a Mac reaches another Mac's engine with it over ssh, and an engine reaches the guest inside each VM with it ([ADR-016](../decisions/016-api-v2-and-remote-by-api.md)). Where a call runs is [Architecture](../concepts/architecture.md#the-router)'s.

| Section                | Answers                                                             |
| ---------------------- | ------------------------------------------------------------------- |
| The transport          | The sockets and the ssh bridge the frames travel on                 |
| The frames             | One JSON object per line, and what each key means                   |
| calls.json             | The list of calls, generated from the Registry and the engine's own |
| packages/api           | Every call's schema and the TypeScript types, generated             |
| The engine's own calls | What a process of this Mac asks of the engine's live state          |
| Errors                 | The error object and its codes                                      |

## The transport

| From                  | To                   | How                                                                                                                                                         |
| --------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a process of this Mac | this Mac's engine    | the unix socket `~/.local/state/station/engine.sock`, mode 0600 (`remote/adapter/unix`)                                                                     |
| this Mac              | another Mac's engine | `ssh -o BatchMode=yes <mac> station engine attach`, which bridges ssh's stdio to that Mac's socket (`remote/adapter/sshstdio`)                              |
| a Mac's engine        | a VM's guest         | `station guest serve --stdio`, run over the engine's one guest connection to the VM                                                                         |
| a process in a VM     | its Mac's engine     | the guest's socket `~/.local/state/station/guest.sock` inside the VM, relayed to its Mac's engine over that same connection; the VM holds no key to its Mac |

The engine listens on no TCP port, and the reserved ports' forwarders bind `127.0.0.1` only (the rule `engine-no-tcp`).

## The frames

A frame (`remote/api.Frame`) carries `v` (2) and `id`. A request carries `hello`, `call` or `watch`, with its `target` (`{name, on}`: the machine, and the Mac a VM runs on) and its `in`; its answers carry the same `id`: `progress` frames (`{task, detail, done, error}`), then one `out` or one `error` for a call, `out` frames then `done` for a watch. The first frame of a connection is `hello`: the far binary's version and the calls it serves, so a call it does not serve is `far-too-old` before it is sent; with them, the `kind` of the machine that answers (`computer`, `workspace` or `server`). The hello a caller sends names its own `version`. Either side refuses a release before `remote/api.Floor` (v3.2.0, the first release of today's words) whatever it serves: the far side as `far-too-old`, the caller's calls as `remote.caller-too-old`, its hello still answered; a build of no release (`dev`, a `git describe` past a tag) passes. A VM's guest server reads its stdin to the end before it answers, so its hello is asked alone before each call. The calls of one connection are answered in the order they came.

```text
→ {"v":2,"id":"7","call":"machines.create-workspace","in":{"Request":{"Image":"linux","Lifetime":"ephemeral"}}}
← {"v":2,"id":"7","progress":{"task":"Booting linux-1"}}
← {"v":2,"id":"7","out":{"VM":{"Name":"linux-1"}}}
→ {"v":2,"id":"8","call":"engine.stop","in":{"Confirm":"inf"}}
← {"v":2,"id":"8","error":{"type":"needs-confirmation","code":"confirm.yes-needed","subject":"stop","message":"refusing without --yes: stop","hint":"re-run with --yes"}}
```

## calls.json

[`apps/engine/remote/api/calls.json`](../../apps/engine/remote/api/calls.json) is the Registry and the engine's own calls, projected by `make generate` (`station.calls/v1`): each call's `name`, the `schema` of its output (`station.<call>/v<n>`, the version of the document `--json` prints, the call's `Document`: `station.machinefile.plan/v2`), its `section`, its `where` (`at-target`, `in-engine`, `in-process`), the confirmation it may require, the `errors` it declares, its input and output types, `watch` for a read that fills progressively, and `own` for a call the engine serves beside the Registry (below). The engine serves every call of it, a Registry's call run on this Mac as the CLI runs it; the menu bar names its actions by these names; `api_test.go` fails when the file differs from the Registry and `enginecalls.Owns`.

## packages/api

[`packages/api/`](../../packages/api/README.md) is the same wire, machine-readable, written by `make generate` from the Go types: `schemas/calls/<call>.json`, one JSON Schema per call of `calls.json` (its `in`, and the `out` of each answer), `schemas/frame.json` (the frames), `schemas/event.json` (the events of a watch of pages), and `index.d.ts`, their TypeScript, with `Calls`, the map a client types `call('ports.list', input)` by. Its drift test fails `make test` when a file and the Go types differ, the recorded streams and page fixtures are checked against its schemas, and `answers-match-schemas` sends every read that asks no confirmation to `guest serve --stdio` of the spec build over each world and checks each answer against its call's schema.

## Errors

An error carries its `type` (which decides the exit code), its `code` (a call's own, `call.unknown`, `call.bad-frame` for a line that is no v2 frame, or the engine's: `unknown_vm`, `temporary`, `not_running`, `range_full`, `max_per_vm`, `ignored_port`, `not_allowed` (a guest's share outside its VM's rights), `guest_timeout`, `internal`, `awake_guard`, `awake_range`, `awake_unsupported`, `unknown_page`), its `subject` and `detail`, a `message` and a `hint`, worded as the CLI prints them. A watch takes its connection: a later line on it gets no answer, so a client sends its calls on a second connection. The first page is the frame (pending values), then a page whenever one changes, coalesced over 250 ms and never resent unchanged; a client that does not read for 5 s is dropped. The pages are `menubar` (Home), `menubar.machine:<name>` (one machine's page, `menubar.machine:infra`), `menubar.ports[:<machine>]` (every Mac's ports, one Mac's and its VMs', or one VM's: what is exposed first, then what is public, private and only listening, a port shared in the last 8 s marked `fresh`), `menubar.awake`, `menubar.activity[:<machine>][:6m|1h|24h]` (This Mac's activity over that window, 1 h unless named, or a named machine's: a Mac's read through its engine, a VM's through the engine of the Mac that runs it; each window's CPU comes folded as its chart draws it, 72 bars of 5 s, 60 of a minute or 48 of 30 min, each with its mean and its busiest share, and the window's peak), `menubar.accounts[:<machine>]` (every Mac's accounts, one Mac's, or the copies a VM's Mac shared with it), `menubar.needs[:<machine>]` (what needs you, then the upkeep, of every machine or of one), `menubar.find` (the Find index), `menubar.agent:<name>` (one agent: its wait or its steps, and the workspace it runs on) and `power`. Each is read only while a client watches it. A page lists in `live` the keys its moving numbers follow (`<measure>:<machine>`, the measures `cpu`, `memory`, `free`, `disk` and `net`: `cpu:linux-1`, a VM's share of its own cores read inside it; and `cpuh:<vm>`, a VM's CPU as a share of the whole Mac that runs it, read on that Mac from the Virtualization process that runs its guest), and each of its values that moves names its key in its own `live`. While a watch is open the engine reads every 2 s the keys of every open page, all watches' at once, and sends each watch one `event` `sample`: `at`, `values` (each of its pages' keys and its value as the page draws it, the measure now led into its series as a `spark` value, `free` alone) and `stale` (the keys whose machine has not answered for more than 30 s, kept at their last value and marked `stale`); so two pages that show one key show one value in one tick. Each machine is asked through its engine, a VM's and another Mac's as the machine page reads them, and a tick waits on a late one for 1 s at most. A page is never rebuilt on a tick, only when its content is read again. Home: the machines (each Mac's Awake with them) every 30 s, Needs you every 15 min or on `refresh`, this Mac's VMs, reserved ports and Awake at once. A machine's page: every 30 s, when the engine's state moves or on `refresh`, each read on that machine, so another Mac's page is that Mac's engine's answer, relayed by this one. A Mac's page carries its segments (Overview, Activity, Ports, Accounts) and every segment's sections at once, so the app picks a segment without a read; a running VM's page carries its own (a server's Overview and Activity, a workspace's four), and a stopped one none; a Mac's Ports ends on its HTTPS links switch (`ports.set-https` on that Mac). A server's page carries Overview and Activity the same way: its facts, the Mac it is on a part whose `nav` is that Mac's page, its Health (folded behind its count while healthy, open by itself while a restart walks its four steps with the one running counted, the down banner with Restart and why, or Stopped with Start), its check's latency over the last hour, its last 30 days, the last lines its console kept while it is down, its gauges (their last values while it cannot answer, waiting while it restarts), its ports (each row copying the address that reaches it: a port declared public the site its check asks when that site is served there, else its name and port), and its `footer` (its ssh and Open in Terminal, which waits with its reason while it cannot answer). A workspace's page lists the agents it hosts, read with `agents.list` through this Mac's engine, each opening its own `menubar.agent:<name>`, read the same way and as often. A machine's Activity carries its three windows at once, read with the page from the history its engine keeps (the day at a minute, the last 6 min at 2 s): 72 points of 5 s, 60 of a minute and 48 of 30 min, each the mean of its span and when it starts in the words a scrub says it (`2 min 35 s ago`, `24 min ago`, `14:00`), with the window's peak and, when the CPU stayed at or above 90 % around it, that run and its sentence (`Peaked 94% at 03:10`, or `CPU on mac-mini has been above 90 % for 12 min` while it holds), the network sent over received, then the memory now and the busiest processes, a Mac's VMs among them; the window picked is the app's own, the hour until one is picked for that machine. A Mac's page reads that Mac's Awake and the copies every Mac shared for its Needs you, folded after three rows, and a Mac not heard from for more than 30 s carries `header.stale` (`seen 40 s ago · checking`) over its last values. Ports, Awake and Accounts: when they open, then every 30 s, when the engine's state moves or on `refresh`, each Mac's through its engine. Accounts lists what needs you, then every copy shared with a VM with its time left and its total (`left`), then every account signed in somewhere with the Macs that hold it, in the order [Accounts](accounts.md) gives. Awake has This Mac's card (its switch, the terms `1 hr`, `4 hr` and `Until 18:00`, none picked while it follows a run, which a line names, and the switches its capabilities allow), the running work that pauses while it sleeps, then one card per other Mac: its policy, what depends on it and its switch, a Mac asleep read as asleep with when it was last seen; it has no footer. Needs you: when it opens, then every 30 s, when the engine's state moves or on `refresh`, the machines, every Mac's ports, accounts and Overview each through its engine; it lists a server down and a port exposed first, then an agent waiting on you, then a copy ending in under 30 min, the soonest first, each a row with its verb, then the upkeep apart (a security setting, what fails, a sign-in, the updates as one row), which the badge never counts. Find: read as Home is read, from the same calls, so it asks nothing Home does not; one entry per row in its group (`needs-you`, `machines`, `ports`, `actions`, `sections`), each with its glyph, its title, where it is (`detail`), its tags (the `tags` cell), its verb (`verb`, whose action's `key` is the entry's), its alternate (`quick`) and the page it opens (`nav`), the needs in Find's words and ranked as Needs you ranks them; `verbs` holds each VM's verbs, a group headed by its name, for a query that begins it. Activity: every 2 s over its window. A machine is sampled every 60 s, and every 2 s only while a client holds `engine.watch` on it, as the menu bar does while its popover is open: a watch of pages or events alone never makes it so. Inside a VM, the guest's socket serves `engine.services`, `engine.reserve`, `engine.release` and `engine.agents-held` in the same frames, relayed to its Mac's engine.
